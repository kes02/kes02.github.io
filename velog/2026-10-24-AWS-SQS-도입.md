메시지 큐를 도입하기로 하고 나서, 그럼 뭘 쓸 것인가를 정해야 했다. 후보는 RabbitMQ, Kafka, 그리고 AWS SQS. 결론부터 말하면 SQS로 채택했고, 우리 상황에서는 나머지 둘이 주는 이점이 비용과 운영 부담이 있었고 현재 서버, 데이터가 AWS에 있기 때문에 우선적으로 고려하게 되었다.

## 개발 상황

- 인프라: ECS Fargate, S3, RDS, EventBridge
- 예산 한도가 월 120 USD로 잡았고, Fargate Spot을 쓰고있다.
- 메시지 양이 적다. 1분 주기 스케줄 두 개가 만드는 게 월 9만 건 수준

## RabbitMQ를 고르지 않은 이유

라우팅이 필요했을 때 선택하였을 텐데, RabbitMQ는 우선순위 큐, topic 기반 분기, headers 매칭 같은 걸 쓸 수 있다. 그런데 우리가 필요한 건 '이 메시지를 저 프로세스가 가져가서 처리한다'가 전부였고 라우팅이라고 할만한 기능이 필요하지 않았다.

Amazon MQ를 쓰면 관리형이지만 시간당 과금이 붙고, 직접 운영하면 Fargate 위에서 상태를 유지하는 컨테이너를 다뤄야 한다. 고가용성까지 가면 부담이 한 단계 더 올라간다. 우리 예산에서 브로커 하나가 차지하는 비중이 컸다...

## Kafka를 고르지 않은 이유

Kafka는 애초에 다른 문제를 푸는 도구다. 같은 이벤트를 여러 소비자가 각자의 속도로 읽고, 필요하면 과거 시점부터 다시 읽는다. 로그 수집이나 이벤트 소싱에서 빛난다. 

우리는 판정 요청 하나를 AI 서버 하나가 가져가서 처리하면 끝이다. 재처리가 필요하면 판정 안 된 건을 DB에서 찾아 다시 큐에 넣으면 되기 때문이다.

Kafka는 소비자가 주기적으로 신호를 보내지 않으면 죽은 걸로 보고 파티션을 재분배한다. 그런데 우리 판정은 한 건에 수백 초가 걸린다. 설정을 잘못 잡으면 처리 중인데 리밸런스가 일어나는데 설정으로 풀 수 있는 문제지만, 안 겪어도 될 문제를 발생하게 둘 필요가 없었다.

## 최종적으로 SQS를 고른 이유

### 서버가 없다

브로커를 띄우지 않는다. Pulumi에 큐 리소스를 선언하면 끝이고, 패치도 모니터링도 장애 대응도 없다. 

### 요청 단위 과금이다

상시 과금이 없다. 메시지를 보낸 만큼만 낸다. 우리처럼 양이 적으면 사실상 무료 구간에 머문다. 나중에 트래픽이 늘면 그때 비용도 같이 늘지만, 그건 사용자가 늘었을 때 다시 고려하면 된다.

### AWS 서비스와 바로 붙는다

업로드 확정 흐름을 보면 이렇다.

```
앱이 presigned URL로 S3에 업로드
  → S3가 EventBridge로 이벤트 발생
  → EventBridge 규칙이 큐로 전달
  → 서버가 큐에서 꺼내 업로드 확정
```

RabbitMQ나 Kafka였다면 S3 이벤트를 받아 브로커로 옮기는 Lambda를 하나 만들어야 했다. 그 Lambda가 또 하나의 장애 지점이 된다. 1분 주기 작업도 마찬가지로 EventBridge Scheduler가 큐에 직접 메시지를 넣는다.

### 재시도와 실패 처리가 지원된다

메시지를 꺼내면 일정 시간 동안 다른 consumer에게 안 보인다. 그 사이에 처리하고 삭제하면 끝난다. 처리에 실패해서 삭제하지 못하면 시간이 지나 다시 보이고 다시 가져간다. 이게 정해진 횟수만큼 반복되면 별도의 데드레터 큐로 옮겨진다. 그래서 메시지가 쌓이면 알람이 울리고 이걸로 모니터링을 할 수도 있다.

### 권한을 IAM으로 다룬다

브로커를 쓰면 계정과 비밀번호를 만들고 어딘가 보관해야 하지만 SQS는 IAM 역할이면 충분하다. 우리는 서비스별로 권한을 좁게 줬다. API 서버는 알림과 탈퇴 큐에만 보낼 수 있고, 소비자 프로세스는 자기가 읽어야 할 큐만 읽는다. 

## 실제 설정과 그 이유

### 가시성 시간 초과

| 큐 | 값 | 이유 |
|---|---|---|
| 판정 큐 | 300초 | 모델 추론이 오래 걸린다 |
| 업로드 확정 | 60초 | S3 이벤트 처리는 짧다 |
| 알림, 주기 명령 | 30초 | 가벼운 작업이다 |

이 값을 실제 처리 시간보다 짧게 잡으면 처리 중인 메시지가 다시 풀려 두 번 처리된다. 판정의 300초는 아직 초기값이고, 모델의 실제 처리 시간이 나오면 조정할 생각이다.

처리가 예상보다 길어질 것 같으면 코드에서 시간을 연장할 수 있도록 그 권한도 같이 줬다.

### 재시도 횟수와 데드레터 큐

5회 실패하면 데드레터 큐로 보내고 거기서 14일 보관한다. 메시지 수가 0보다 커지면 알람이 팀 메일로 오도록 해두었다.

### 주기 명령 큐의 보존 기간

1분마다 명령이 들어가는 큐인데, 보존 기간을 60초로 줄였다.

이유는 consumer가 꺼져 있는 동안에도 스케줄은 계속 돈다. 기본값인 4일을 그대로 두면 consumer가 다시 켜졌을 때 그동안 쌓인 수천 건이 한꺼번에 밀려오기 때문에 60초로 줄이면 못 처리한 명령은 그냥 만료되도록 했다.

## SQS의 한계와 대응

1. **메시지가 최소 한 번 전달된다.** 같은 메시지를 두 번 받을 수 있다는 뜻이다. 네트워크 문제나 소비자 재시작 때 생긴다. 그래서 판정 결과를 저장할 때 (클립 아이디, 모델 버전) 조합에 유니크 제약을 걸기로 했다. 같은 판정이 두 번 들어오면 충돌하고, 충돌하면 갱신한다.

2. **순서를 보장하지 않는다.** 필요하면 FIFO 큐를 쓸 수 있지만 처리량 제한이 따라온다. 우리 판정은 순서가 상관없어서 기본 큐를 쓴다.

3. **메시지 크기가 256KB로 제한된다.** 오디오 파일은 당연히 불가능해서 파일은 S3에 두고 경로만 메시지에 담는다. 

4. **여러 소비자에게 같은 메시지를 뿌릴 수 없다.** 

5. **즉시 응답을 받을 수 없다.** 메시지를 넣고 그 자리에서 답을 받는 구조가 아니다.

## 정리

SQS가 가장 좋은 메시지 큐라서 고른 게 아니고 현재 AWS에서 인프라를 구성해두었고, 우리가 원하는 기능은 큐에 요청을 담아두고 처리할 수 있을 때 처리해서 사용자에게 보여주는게 다였다. 

만약 초당 수만 건씩 큐가 발생하고 느려진다면 그 때는 다시 어떤 요구사항을 채택해야할지 고려해야할 것이라고 생각한다.
또한, 얼마되지 않은 사용자들이 이용하는 서비스인데 큐를 도입하는게 과설계가 아닐까 라는 고민도 하였으나, 이는 비즈니스 설계에 있어서 사용자들에게 어떻게 빠르게 전달할지, 추후에 사용자가 늘었을 때 어떻게 대처해야할지 등을 고민하며 자연스럽게 고민이 해소되게 되었다.
