> 다음 편에서 VAD+AEC와 Silero(Open source)로 이어간다.

개발한 서비스는 [버디버드](https://buddybird.xyz/ko/)로 앵무새에게 말을 가르치는 앱이다. 사용자는 단어 목록에서 단어를 녹음하거나 Preset으로 제공되는 단어를 선택하고 세션을 실행하며 정해진 시간동안 반복해서 들려주며 앵무새가 따라 하도록 유도한다. 이때, **앵무새가 '따라 했는지'를 알려면, 앵무새가 언제 소리를 내는지부터 알아야 한다.**

마이크를 계속 켜두고 통째로 녹음하면 될 것 같지만, 실제로 그 파일을 열어보면 대부분이 무음일 것이다. 그리고 녹음본에는 에어컨 소리, TV 소리, 사람 말소리 등 다양한 소리가 섞이게 될 것이고 그중 앵무새 발화는 몇 초 안될 것이다. 그래서 우리에게 녹음을 위해 당장 필요한 건 **소리가 나는 구간만 잘라내서 녹음본을 저장하는** 것이다. 이걸 **VAD(Voice Activity Detection)**라고 부른다.

먼저 이번 글은 VAD를 무거운 ML 모델 대신 **가볍게 직접 만든 이유와, 그 선택으로 발생한 문제, 그리고 녹음본을 직접 측정**해보았다.

## ML VAD를 붙여야할까?

VAD라고 하면 보통 Silero VAD나 WebRTC의 VAD를 먼저 떠올리고 AI도 이 방안을 추천해준다. 이미 성능이 검증되어 있고, 사람 음성을 배경 소음에서 꽤 잘 골라낸다. 그래서 처음엔 당연히 이 방향을 적용할 생각이었다.

그런데 상황을 하나씩 놓고 보니 마음이 바뀌게되었다.

- **Expo/React Native 위에서 돌아야 한다.** ONNX 모델을 온디바이스로 돌리려면 런타임을 얹고 iOS·Android 네이티브를 맞춰야 한다. MVP 단계에서 이 비용을 치르는 것은 너무 과하다는 생각이 들었다.
- **실시간이어야 한다.** 세션 중에 100ms 간격으로 "지금 소리가 나는가"를 판단해야 한다.
- **결정적으로 우리가 잡으려는 건 _사람 음성이 아니다._** Silero 같은 모델은 사람 발화에 최적화되어 있다. 그리고 우리가 구분해야할 앵무새 소리는 스펙트럼이 다르다. 그래서 이미 검증된 모델이 우리 서비스에 적합하지 않다는 생각이 들었다.

정리하면, ML VAD는 정확도라는 강점이 있지만 그 강점이 **사람 목소리를 구분할 때는 확실했지만 앵무새의 발화를 구분하는데 있어 강점이 사라졌다.** 그래서 일단 MVP 단계에서는 경량 방식을 적용하고, 데이터가 쌓여 좀 더 많은 테스트를 진행할 수 있고 의미 있는 정확도가 보일 때 ML로 넘어가자로 결론을 내렸다.

## 경량 VAD, 소리 크기(metering)만으로 판정하자

Expo 레코더는 녹음 중에 metering 값을 받는데, 마이크로 들어오는 소리의 크기를 dB로 알려주는 값이다. **이 dB가 일정 수준 이상으로 꾸준히 유지되면 '발화 중', 아래로 꾸준히 떨어지면 '발화 끝'으로 보는 것이다.**

핵심은 '일정함'에 있다. 문 닫는 소리(=일시적인 소리) 한 번에 발화가 시작됐다고 판단하면 안 되고, 말 중간의 짧은 숨 고르기에 발화가 끝났다고 잘라도 안 된다. 그래서 순간적인 값이 아닌 **연속된 샘플 수를 세도록 하였다.** 실시간 감지부는 이렇게 생겼다.

```ts
const VAD_DB_FLOOR = -60;
const VAD_DB_CEIL = -10;

export const VAD_THRESHOLD = 0.35;        // 정규화 진폭 임계값
export const VAD_SUSTAIN_SAMPLES = 3;     // 연속 초과 3샘플 → 발화 시작 (≈300ms)
export const VAD_RELEASE_SAMPLES = 5;     // 연속 미만 5샘플 → 발화 종료 (≈500ms)

export function stepVad(state: VadState, normalized: number): VadTransition {
  if (normalized >= VAD_THRESHOLD) {
    state.aboveRun += 1;
    state.belowRun = 0;
  } else {
    state.belowRun += 1;
    state.aboveRun = 0;
  }
  if (!state.isVoice && state.aboveRun >= VAD_SUSTAIN_SAMPLES) {
    state.isVoice = true;
    return 'onset';
  }
  if (state.isVoice && state.belowRun >= VAD_RELEASE_SAMPLES) {
    state.isVoice = false;
    return 'release';
  }
  return null;
}
```

`stepVad`는 샘플 하나를 받아 상태를 한 칸 전진시키고, 경계를 넘었을 때만 `onset`이나 `release`를 돌려준다. 이때, 시작(sustain 3)보다 종료(release 5)를 더 길게 잡았는데 단어가 아닌 문장으로 말할 수 있기 때문에 종료를 너무 민감하게 두면 한 마디를 여러 조각으로 잘라버릴 수 있기 때문이다.

## 경량 VAD 채택으로 발생한 트레이드오프

경량 VAD를 택하면서 정확도를 애매해진 대신 다른 문제들도 있었다. 당장 해결해야할 치명적인 문제는 아니었지만, 사용자들에게는 당장 앵무새가 발화했을 때의 녹음본 제공이 어려워졌다.

**첫째, 경량 VAD는 소리의 '크기'만을 본다.** 말인지 소음인지는 구분하지 못한다. 에어컨을 세게 틀어놓으면 그 소음이 임계값을 넘어 발화로 잡힌다. 이는, metering 기반의 근본적 한계였다. 그래서 이걸 항상 켜두는 대신, 세션 흐름상 앵무새가 **소리 낼 법한 구간(레퍼런스를 들려준 직후의 갭)** 에서만 선택적으로 돌리는 쪽으로 우회했다.

**둘째, 재생과 녹음이 겹치면 스피커 소리를 발화로 오인한다.** 학습 목표 단어를 스피커로 들려주는 동안 마이크는 그 소리를 그대로 듣게 된다. 이때, 에코 제거(AEC)를 쓰지 않았기 때문에, 겹침 구간은 아예 '제외 구간'으로 빼버리는 방식으로 처리했다. 이 결정이 정당한지는 뒤에서 숫자로 확인한다.

**셋째, 고정 임계값 0.35는 보편 상수가 아니다.** 기기마다 마이크 게인이 다르며, 어떤 폰에서 잘 잡히는 값이 다른 폰에서는 둔감하거나 예민하다. 이건 실시간 감지엔 큰 문제가 아니지만('지금 말하는 중인가'는 이분법이라 어느 정도 관대해도 된다), 녹음이 끝난 뒤 **실제로 세그먼트를 잘라 저장하는 단계**에서는 치명적이다. 그래서 저장용 분할은 고정 임계값을 버리고 **녹음마다 임계값을 다시 계산하는 적응형**으로 갔다.

```ts
// segmentMetering: 이 녹음의 실제 동적 범위에 상대적으로 임계값을 잡는다
const floor = percentile(levels, 0.15);   // 대략 바닥 소음 레벨
const peak  = percentile(levels, 0.95);   // 대략 발화 피크
if (peak - floor < MIN_RANGE) return [];  // 동적 범위 없음 → 분할 포기
const threshold = floor + 0.4 * (peak - floor);
```

게인이 낮은 기기는 floor·peak가 통째로 낮게 잡히고, 임계값도 그에 맞춰 내려간다. 이렇게 되면 고정 임계값이 0.35였다면 아무것도 못 잡았을 상황이 적응형에서는 정상 동작한다. 

## 측정 도구를 만들었다

여기까지는 _그럴듯한 설계_ 다. 그래서 검증을 위해 별도의 **측정 도구**를 파이썬으로 개발해보았다.

핵심 검증은 레퍼런스와 녹음본을 **합성**하는 것이다. 실제 녹음은 '어디가 진짜 발화인지'를 사람이 일일이 라벨링해야 하지만, 직접 합성하면 정답을 처음부터 알 수 있다.

```
near_end (마이크 신호) = 사용자 발화 + 재생 에코(지연·감쇠·잔향) + 잡음
far_end  (AEC 레퍼런스) = 깨끗한 레퍼런스
```

이렇게 '스피커가 울리는 방에서 따라 말하는 상황'을 코드로 만들고, 사용자 발화를 넣은 위치를 정답으로 둔다. 그런 다음 경량 VAD가 뽑아낸 구간을 정답과 **10ms 프레임 단위로 비교해 F1과 IoU**를 잰다. 도구 안의 알고리즘은 앱의 실제 코드(`vad-segmentation.ts`)를 상수까지 그대로 포팅해서, 여기서 나온 숫자가 앱 동작을 대변하도록 맞췄다.

앱 기본 레퍼런스 음원 4종을 사용자 발화 자리에 번갈아 놓고, 버디버드의 실제 설계인 **레퍼런스 → 갭 → 발화** 비겹침 시나리오로 도구를 돌린 결과다.

| 파이프라인 | F1 (평균) | F1 (범위) | IoU (평균) |
|---|---|---|---|
| 경량 VAD (+AEC) | **0.90** | 0.87 ~ 0.93 | 0.83 |
| Silero VAD | 0.97 | 0.92 ~ 0.99 | 0.93 |

이 결과값들로 두 가지를 확인할 수 있었다.

**하나, 이 갭 시나리오에선 AEC가 사실상 동작하지 않는다.** 확인차 AEC를 끄고도 돌려봤는데 갭 구간의 F1이 그대로였다. 사용자는 갭에서만 말하고, 그 갭엔 애초에 에코가 없다. 에코를 지우는 AEC가 지울 게 없으니 결과가 같은 거다. 이게 **'AEC 없이 경량 VAD만으로 먼저 출시한다'는 결정이 이 시나리오에선 손해가 아니었다는 증거**다. AEC가 필요해지는 건 발화가 재생과 겹치는 순간부터인데, 그 이야기는 다음 글로 미룬다.

**둘, Silero는 0.97로 더 정확하다.** 경량 VAD가 0.90, 어려운 단어에선 0.87까지 내려간다. 진폭만 보는 방식의 한계가 숫자로 드러난 지점이다. 그러면 정확도가 더 높아야할 때 Silero VAD를 사용하면 된다.

> 이 숫자들은 **합성 시나리오** 기준이다. 앱 레퍼런스 음원을 사용자 발화 자리에 놓고 에코와 잡음을 입혀 만든 값이라, 실제 앵무새 발화의 현장 정확도와는 다르다. 파이프라인 사이의 **상대 비교**로 읽는 게 맞다.

### 두 층위로 검증했다

측정 도구가 시스템 전체의 정확도를 봤다면, 그 아래에서 판정 로직 자체는 **순수 함수**로 검증했다. `stepVad`는 상태와 입력값을 받아 전이를 반환할 뿐 레코더나 파일 시스템을 건드리지 않는다. 가짜 진폭 시퀀스를 넣고 어떤 전이가 나오는지만 확인하면 된다.

```ts
const state = createVadState();
stepVad(state, 0.6);              // 1틱 — null
stepVad(state, 0.6);              // 2틱 — null
stepVad(state, 0.6) === 'onset';  // 3틱 — 발화 시작
stepVad(state, 0.1);             // 짧은 무음 한 틱
stepVad(state, 0.6);             // 다시 소리 → belowRun 리셋, 발화 유지
```

이 순수 함수의 이점은 리팩터링에서 확실히 드러났다. 처음엔 "따라하기 갭"용과 "쉬는 구간"용 VAD를 각각 만들었는데, 둘이 사실상 같은 산술을 쓰고 있었다. 각자 카운터를 세 개씩 들고 있던 걸 하나의 `VadState`로 합쳐 detector 하나로 추출했더니, 중복이 사라지면서 튜닝 상수도 한 곳에서 관리하게 됐다.

## 지금은 이걸로 충분한가?

경량 VAD는 '완벽한 해법'이 아닌 'MVP 단계에서의 최선의 해법'이다. 오탐이 있고, 진폭만 보고, 어려운 단어에선 F1이 0.87까지 떨어진다. 그런데도 비용이 낮고, 실시간으로 돌고, 판정 로직이 투명하고, 무엇보다 우리 시나리오에서 F1 0.90이 나온다는 걸 측정으로 확인했다.

그래서 '정확도가 더 필요하면 Silero'라고 결정하려던 차에, 한 가지가 걸렸다. 지금까지의 측정은 '사용자 발화' 자리에 전부 **사람 목소리**를 놓고 잰 값이다. 그런데 버디버드가 실제로 잡아야 하는 소리는 사람이 아니라 **앵무새 소리**다.

사람 음성으로 학습된 Silero는, 앵무새 소리를 얼마나 잡을까? 이 질문에 실제 앵무새 녹음으로 답해보니 숫자가 통째로 뒤집혔다.
