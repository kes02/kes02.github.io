앵무새 소리인지/아닌지 분류 모델을 개발하면서 우리는 Perch 2.0 모델을 백본으로 사용했다. 그리고 최근 이 모델이 Pytorch로 작성된 깃헙을 발견했다.

## 배경

데이터 라벨링 1시간 못합니다.. 그래서 만들었습니다. 앵무새 흉내 라벨링을 위한 분류 모델을 만들었다고 언급했었다. 

실제로 라벨링을 해보았을 때 아무리 빠르게 해도 0.5초 클립 100개에 약 1시간이 걸렸다. 그리고 3.3G 3시간 분량의 데이터를 이 속도로는 감당하지 못할 것이 분명했다. 그래서 분류가 가능한 모델 개발을 계획하고 검증해보았다.

우리는 이 모델의 인코더로 구글의 Perch v2를 사용했다. Perch v2는 32kHz 5초 오디오에서 1536차원 임베딩을 생성하고, 그 임베딩에 우리가 학습시킨 로지스틱 회귀를 결합해 두 가지를 판별한다.

- 판별 A: 앵무 흉내와 사람 말 구분
- 판별 B: 앵무 흉내와 울음 구분

## 간단한 비교

두 backbone은 같은 onnx 파일에서 비롯한다. 그래서 정확도 비교는 무의미하다.

| 구분 | 기존 perch2 | PyTorch 포팅 |
| --- | --- | --- |
| 출처 | perch_v2.onnx | 같은 perch_v2.onnx |
| 실행 | ONNX Runtime | onnx2torch로 변환한 PyTorch 모듈 |
| 임베딩 | 1536차원 | 1536차원 |
| 학습 | 불가, autograd 없음 | 가능, backbone까지 미분 |

onnx2torch는 그래프의 각 노드를 등가 PyTorch 연산으로 변환한다. 구조를 새로 추측하지 않으므로 임베딩 값이 같다. 같은 가중치를 형식만 변경한 결과이기 때문이다.

그래서 단순히 인코더만 변경해 정확도를 측정하면 결과가 항상 같다. 왜냐하면 포팅이 더하는 기능은 backward 하나뿐이기 때문에 '둘이 실제로 무엇이 다른지'로 관심을 옮겼다.

## 아래는 비교해본 결과이다.


### 다운스트림 정확도

판별 A를 조건별로 평가했다. 세 조건 모두 두 backbone의 정확도 차이가 0.000이다.

![](https://velog.velcdn.com/images/kes02/post/1d68c167-57bd-4bf9-8cea-f9c280206567/image.png)

| 조건 | onnxruntime | PyTorch 포팅 | 차이 |
| --- | --- | --- | --- |
| ① 카페 안 | 0.966 | 0.966 | 0.0000 |
| ② 단어로 배워 카페 | 0.939 | 0.939 | 0.0000 |
| ③ 통합 | 0.972 | 0.972 | 0.0000 |

평가 방법은 로지스틱 회귀와 LeaveOneGroupOut으로 고정하고 임베딩이 같으므로 사진처럼 예측도 같다.

### 속도
onnxruntime이 CPU에서 PyTorch 포팅보다 14배 빠른 결과를 보였다.
![](https://velog.velcdn.com/images/kes02/post/4141374e-e582-4b0a-824b-25f227cd84e3/image.png)

| backbone | 클립당 |
| --- | --- |
| onnxruntime | 26.7 ms |
| PyTorch 포팅 | 369.6 ms |

onnx2torch는 그래프를 파이썬 레벨 모듈로 전개한다. 그래서 런타임 최적화가 붙은 ONNX Runtime의 속도를 따라가지 못해서 다음과 같은 결과가 나오게 되었다.
테스트: m4 pro 24g 기준

### 처리 시간 환산

실험에 사용한 오디오는 1.40시간으로 카페 원본 82.6분과 단어 클립 1.4분과 미리 다운 받아둔 S3 데이터 3시간으로 비교해보았다.

| 대상 | 5초 창 | onnxruntime | PyTorch 포팅 |
| --- | --- | --- | --- |
| 실험 데이터 1.4시간 | 1008개 | 27초 | 6.2분 |
| S3 데이터 3시간 | 2160개 | 58초 | 13분 |

확실히 기존 모델은 3시간 분량을 1분 안에 처리했고, pytorch의 경우 데이터가 늘수록 두 backbone의 14배 차이가 누적되어 차이가 커졌다.

## 파인튜닝

이 데이터에서는 파인튜닝이 frozen 임베딩을 이기지 못한다.

onnx는 backward가 없어 backbone을 학습하지 못한다. 그러나 PyTorch 포팅이 있어 파인튜닝을 고려할 수 있었다. 그래서 판별 A에서 직접 시험했다.

![](https://velog.velcdn.com/images/kes02/post/f43c8a88-8f87-4d28-a127-6b8f3eda016c/image.png)

라벨링 되어 있는 앵무새가 따라하는 단어 41개로 학습하고, 랜덤으로 카페 녹음 데이터 179개를 맞히는 배포 조건에서 균형정확도를 비교했다.

| 모델 | 학습 범위 | 균형정확도 | 흉내 재현율 | 사람 재현율 |
| --- | --- | --- | --- | --- |
| baseline | 헤드만 | 0.941 | 0.94 | 0.94 |
| partial-FT | 마지막 3블록과 헤드 | 0.923 | 0.89 | 0.96 |
| full-FT | 전체 backbone과 헤드 | 0.873 | 1.00 | 0.75 |

partial-FT는 baseline과 균형정확도가 같은 수준이었다. 카페 표본이 흉내 18개, 사람 161개로 편향돼 원정확도는 다수 클래스에 좌우되게 되고, 공정한 균형정확도로 보면 오히려 낮은 것 같다.

full-FT는 성능이 확 떨어졌는데, 사람 말을 흉내로 오인해 사람 재현율이 0.75로 학습 데이터 41개에 과적합된 것 같았다.

특히, 두 파인튜닝 모두 몇 epoch 만에 train 정확도 1.000에 도달하는 것으로 당장은 표본이 작아 backbone을 학습하면 과적합이 발생하여 오히려 frozen보다 떨어진 다는 것을 확인했다.

카페 안 LeaveOneGroupOut으로 검증하는 조건 ①은 정확도 차이가 크지 않아 추후에 데이터가 많이 쌓인다면 확인해봐도 좋을 부분 같다.

## 결론

데이터가 적은 상황에서는 기존 모델, 데이터가 쌓여서 학습시킬 수 있다면 pytorch로 파인튜닝시켜보는 것도 좋을 것 같다.

| 상황 | 선택 |
| --- | --- |
| 추론, frozen 임베딩과 분류기 | onnxruntime, 결과가 같고 14배 빠름 |
| 지금 데이터로 파인튜닝 | 하지 않음, 과적합만 발생 |
| backbone 학습이 필요할 때 | PyTorch 포팅, onnx는 불가능 |

결국 pytorch를 사용하기 위해 필요한 조건은 아래 3가지 이다.

1. 라벨이 충분히 많아 과적합하지 않는 규모
2. GPU
3. backbone 적응이 실제 이득을 내는 과제
