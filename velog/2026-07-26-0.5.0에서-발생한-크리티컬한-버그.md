평소처럼 firebase를 보던 중 Crashlytics에 fatal 하나가 올라온 것을 확인했다. 안드로이드 사용자가 학습 세션 도중 앱을 벗어났다 돌아오면 **하얀화면과 함께 앱이 죽는다**는 것이었다. 크래시를 발생시키기 위해 따라 하니 실기기에서 생각보다 재현이 잘 안 됐다. 그 이유는 특정 시간 이상 포그라운드에 있다가 복귀하면 발생하는 것이 아니었다. 그래서 버그가 있다는 것을 찾기가 쉽지 않았다.

## 증상: firebase의 스택트레이스 한 장

Crashlytics에 올라온 fatal은 아래와 같았다.

```
Fatal Exception: io.invertase.firebase.crashlytics.JavaScriptError:
Call to function 'AudioPlayer.play' has been rejected.
→ Caused by: The 1st argument cannot be cast to type expo.modules.audio.AudioPlayer
  (received class java.lang.Integer)
→ Caused by: Cannot use shared object that was already released
    at .play((native):0:0)
    at .anonymous(address at index.android.bundle:1:2172313)
    at .tryCallOne(address at InternalBytecode.js:1:1180)
```

읽어보면 바로 보이는 것이 두 개가 있다.

- **`Cannot use shared object that was already released`**
이미 해제된 네이티브 객체에 접근했다. `java.lang.Integer`는 네이티브 객체가 사라진 뒤에도 JS 래퍼가 들고 있던 shared-object id다. 즉 JS는 player 라고 믿고 호출했는데, 그 자리엔 정수 id만 남고 실행할게 없었다는 것이다. 즉, 빈 박스를 가리키면서 빈 박스가 아닐거라고 믿고 있었다는 것
- **`tryCallOne`** 
Hermes 엔진의 promise 내부 함수다. 이것은 문제의 `play()`가 `.then`이나 `.catch` **콜백 안에서** 호출됐다는 뜻이다.

앱의 학습 세션은 사용자가 설정한 음성을 반복해서 들려주고, 재생 사이의 무음 갭(follow-gap)에 앵무새가 따라 말하도록 기대한다. 그리고 갭이 끝나면 다시 설정한 음성을 반복 재생해준다. 이때, 갭 이후에 재생이 발생하는 부분이 `replayAfterGap`이고, 문제의 `play()`가 여기 있었다.

## 확인된 트리거가 틀렸다

우리가 확인한 버그의 재현 증상은 다음과 같았다.

> 세션 실행 중 중단 후 홈 화면에 복귀해서 여러 앱 사용하거나 임의로 정한 3분이라는 시간을 홈에서 머물다가, 다시 앱으로 복귀했을 때 하얀 화면과 함께 크래시

세션을 켜고, 홈 버튼을 누르고, 다른 앱을 사용하다가, 1분 뒤 백그라운드에 재생 중인 앱으로 돌아왔다. **크래시가 안 났다.** 세션은 그대로 이어지고 있었다.

그 이유에 대해 고민하던 중 백그라운드/포그라운드 전환으로는 세션 화면이 **언마운트되지 않는다.** 화면이 살아 있으면 플레이어도 해제되지 않는다. 해제된 객체가 없으니 "released shared object" 에러가 날 리가 없다. (참고로 개발자 옵션 `always_finish_activities`를 켜면 RN 인스턴스가 통째로 파괴되는데, 그러면 JS 자체가 사라져서 역시 JS 크래시는 안 난다.)

그럼 어떤 상황에서 화면이 언마운트되었는데, `status`는 살아 있을지 찾아봐야했다. 그 결과 **재생 사이 갭 도중에 하드웨어 뒤로가기로 세션 화면을 빠져나가는 상황**에서 발생하는 것이었다. 

```
14:20:56.721  GAP OPEN
14:20:56.820  sessionPlayer effect UNMOUNT/cleanup          ← 뒤로가기로 라우트 pop
14:20:56.821  [cleanup] AudioPlayer.pause has been rejected
              → Cannot use shared object that was already released
14:20:56.832  replayAfterGap called  'running' 'learning'   ← 가드 통과
14:20:56.836  catch branch, retrying play()                 ← seekTo 거부
14:20:58.863  Error: Call to function 'AudioPlayer.play' has been rejected.
              → Cannot use shared object that was already released
```

## 원인: 세 가지의 특정 순서

크래시는 세 가지의 특정 순서가 일치할 때 발생한다.

1. **expo-audio가 먼저 정리한다.** `useAudioPlayer`는 내부적으로 `useReleasingSharedObject`를 쓰는데, 이게 언마운트 cleanup에서 **네이티브 플레이어를 release**한다. 실제로 우리 cleanup의 pause()부터 이미 ERR_USING_RELEASED_SHARED_OBJECT로 거부되는 게 로그에 찍힌다. 즉 언마운트가 시작되는 순간 이미 플레이어는 없다.

2. **VAD cleanup이 뒤늦게 발생한다.** follow-along VAD의 cleanup은 `recorder.stop()` + `configurePlaybackAudioMode()`라는 async 체인을 돌린 뒤 `onGapClosed()`를 부른다. 이 호출은 **언마운트가 끝난 뒤에** 도착한다.

3. `onGapClosed`는 곧 `replayAfterGap`이고, 여기엔 `status !== 'running'` 검사가 있었다. 그런데 이건 **낡은 클로저 값**이지 '플레이어가 아직 살아 있는가'를 묻는 게 아니다.
   - `종료` 버튼을 누르면 `stop()`이 status를 `idle`로 바꿔서 우연히 걸러진다.
   - 안드로이드의 **뒤로가기(라우트 pop)** 는 status를 `running`인 채로 둔다 → 검사를 그냥 통과한다.

그 결과 이미 죽은 플레이어에 `seekTo()`가 걸리고, 거부되고, `.catch`가 **`play()`를 재시도**하는데, 그 rejection을 받아줄 핸들러가 없었다.

```ts
sessionPlayer
  .seekTo(0)
  .then(() => sessionPlayer.play())   // play()의 promise를 체인에서 버린다
  .catch((error) => {
    reportError(error, { scope: 'training.sessionPlayer.gapReplay' });
    sessionPlayer.play();             // ← 죽은 플레이어에 재시도. 이 rejection은 아무도 못 받는다
  });
```

## 왜 안드로이드에서만 크래시가 발생했을까

'iOS엔 백그라운드 라이프사이클 처리가 달라서 안 터지나 보다' 싶었는데, `expo-audio`의 iOS 쪽(`AudioModule.swift`)에도 `OnAppEntersBackground`/`OnAppEntersForeground`가 있었다. 플랫폼에 따른 차이가 아니었다.

그래서 iOS는 코드상 재현을 시도했고 **iOS도 똑같이 터질 가능성이 있었다.** `handleStop`의 `session.stop()` 한 줄을 임시로 지워서 'status 리셋 없는 pop'을 만들어주자, 갭 도중 화면을 벗어나는 순간 바로 크래시가 났다. iOS 스택은 던지는 지점을 더 친절하게 가리킨다.

```
catch branch, retrying play()
  Error: The 1st argument cannot be cast to type SharedObject<AudioPlayer>
  → Unable to find the native shared object associated with given JavaScript object
   > 66 |  sessionPlayer.play();
   sessionPlayer.seekTo.then._catch$argument_0 (use-session-audio-player.ts:66:27)
```

그러니까 **코드 버그는 플랫폼에 관계없이 다 있었다.** 다만, iOS에서 크래시가 없었던 건 순전히 세션 화면을 벗어나는 UI 경로가 다르기 때문이었다.

- **안드로이드**: 하드웨어 뒤로가기 버튼으로 언제든 라우트를 pop할 수 있다. `session.stop()`을 안 거치니 status가 `running`인 채 언마운트 → 낡은 가드 통과 → 크래시.
- **iOS**: 세션 화면을 벗어나는 유일한 길이 `종료` 버튼이고, 그게 status를 `idle`로 만든다 → 가드가 걸린다. 게다가 세션 화면은 라우트 애니메이션이 `fade`라 엣지 스와이프 백 제스처가 아예 안 먹는다고 하였다.

같은 스와이프가 `slide_from_right` 애니메이션인 다른 화면에선 정상 pop되는데, 세션 화면(`fade`)에선 아무 일도 안 일어난다. 즉 **iOS의 안전은 설계가 아니라 운 좋게 발견되지 않은 것**이다. 누군가 이 화면 애니메이션을 바꾸거나 `gestureEnabled`를 켜는 순간 iOS에서도 크래시가 발생하는 것이었다.

## 린트가 왜 못 버그를 확인하지 못 했을까?

`play()`는 Kotlin·Swift 양쪽 모두 **동기 `Function`** 이고, TypeScript 타입이 `void`다. 문제의 본질은 promise를 안 기다렸다가 아니라 **'에러 핸들러가 그 안에서 또 에러를 던진다'** 는 것이다. 이걸 잡아주는 정적 규칙은 없기 때문에 직접 재현해보면서 찾아야했던 버그였다.

### 수정

`await` 뒤에 오는 모든 `play()` 앞에서 **언마운트 여부를 직접 확인**하고, `.catch` 안의 재시도 `play()`를 제거했다. 그리고 버려지던 `play()`의 promise를 단일 catch로 흐르게 했다.

```ts
const isUnmountedRef = useRef(false);

const replayAfterGap = useCallback((): void => {
  if (isUnmountedRef.current) return;                 // 언마운트 후면 즉시 중단
  if (status !== 'running' || phase !== 'learning') return;
  sessionPlayer
    .seekTo(0)
    .catch((error: unknown) => {
      reportError(error, { scope: 'training.sessionPlayer.gapReplay' });
    })
    .then(() => {
      if (isUnmountedRef.current) return;             // await 뒤 다시 확인
      return sessionPlayer.play();                    // promise를 체인에 되돌린다
    })
    .catch((error: unknown) => {
      reportError(error, { scope: 'training.sessionPlayer.gapReplay' });
    });
}, [status, phase, audioUri, sessionPlayer]);
```

언마운트 플래그는 이렇게 세팅한다. deps를 비워야 하는 이유가 하나 있다.

```ts
useEffect(() => {
  return () => {
    isUnmountedRef.current = true;
  };
}, []); // sessionPlayer를 deps에 넣으면 source 교체로 플레이어가 바뀔 때도
        // cleanup이 돌아 플래그가 영구히 latch된다 → 정상 재생까지 막힌다
```

같은 오류가 setup effect에도 있어서 함께 고쳤고, 오디오 미리듣기 훅(`playPreview`)에도 같은 가드를 넣었다. 

| | 수정 전 (Android) | 수정 후 |
|---|---|---|
| `AudioPlayer.play` 미처리 rejection | 1건 | 0건 |
| `AudioPlayer.seekTo` 거부 | 1건 | 0건 |
| 갭 재생 루프 정상 동작 | ✓ | ✓ (회귀 없음) |

iOS도 `session.stop()`을 동일 조건에서 재검증해, `retrying play()` 2건·`'play' function has failed` 1건이 모두 0건이 되는 걸 확인했다.

## 느낀점

버그 리포트에 올라온 것만 믿고 재현하지 않은 후 수정하지 말아야되겠다는 생각을 하게 되었다. 코드 단에서는 당장 해결될 수 있어도, 재현했을 때 맞닥드리는 버그와 달랐기 때문이다.

- 백그라운드/포그라운드 전환이 트리거다 → X, 홈 버튼으론 언마운트가 발생하지 않는다. 
- 이 버그는 안드로이드에서만 발생할 수 있는 특수 조건 → X, iOS도 조건만 만들면 똑같이 발생한다.
- iOS는 플랫폼 코드가 달라 안전하다 → X, 라우트 애니메이션 때문에 우연히 발생하지 않았다.

RN에서 네이티브 shared object의 수명과 async cleanup이 경쟁할 때, 이미 해제된 객체에 접근 크래시는 정적 분석의 사각지대에 숨는다. 결국 로그를 붙이고, 조작을 하나씩 바꿔가며 재현하고, 반증하는 수밖에 없었다. 이 일로 사람이 일일이 실기기로 테스트 할 수 없기 때문에 더더욱 E2E 테스트에 대한 필요성이 올라가는 것 같다.
