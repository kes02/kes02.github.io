## IAM 계정

이건 사실 AWS로 서버를 배포하면서 많이 들어본다. 말 그대로 Admin에서 역할을 조금 나눠서 부여 받은 계정인건데, 현재 서비스 중인 앱의 백엔드는 현재 S3만 존재하기 때문에 'S3에 파일을 업로드 한다'라는 역할만 부여받은 IAM 계정이 있고, 그게 클라이언트 쪽에 키를 발급해줘서 클라이언트가 그 키로 S3에 데이터를 직접 업로드 하고 있다.

그래서 Role based Access Control인가? 라고 생각했는데, 그것보다 좀 더 좁은 지점인 Attribute-based(속성)가 좀 섞인 형태라고 이해하면 된다고 한다. 즉, IAM 계정에서 Post만 받았다면 Post만 가능한 형태인 것.

### 이 구조는 나중에 수정해야하는 부분이다.

정리하다가 걸린 부분은 클라이언트가 IAM 키를 직접 들고 S3에 올리는 구조는 위험하다. 키가 앱 안에 들어가는 순간, 앱을 받은 사람은 누구든 그 키를 꺼낼 수 있다. 꺼내면 우리 버킷에 아무나 업로드가 가능해진다. 권한을 업로드로 좁혀놨어도 남의 파일을 덮어쓰거나 용량 폭탄을 넣는 건 막지 못하게 된다.

정석은 키를 클라이언트에 아예 주지 않는 것이다.

- 서버가 presigned URL을 발급해주고 클라이언트는 그 URL로만 올린다. URL에 유효시간이랑 올릴 경로가 박혀있어서 딱 그것만 가능하다.
- 아니면 Cognito 같은 걸로 짧게 살아있는 임시 자격증명을 받는다.
	- 이 부분도 해본 적 없는 부분이기 때문에 따로 찾아봐야할 것 같다.

## 그래서 S3가 뭔데? 
### (Simple Storage Service) = 저장소

처음에 이것도 RDS와의 차이점이 뭘까 라는 생각을 했다. 그런데 그냥 단순하게 본다면 RDS는 정형화된 테이블을 가지는 DB를 소유하는 공간인 것이고, S3는 파일만을 저장하고 폴더형으로 저장되는 부분이었다. 참고로 S3의 폴더는 진짜 폴더가 아니라 파일 이름에 슬래시가 들어가 있어서 폴더처럼 보이는 것뿐이라고 한다.

추후 RDS를 세팅한다면 S3와 RDS는 어떻게 연결(?)을 할 것인가? 라는 생각을 했는데 찾아보니 이 둘은 이어지는 관계는 아니었다. 서로 모르는 상태로 보통은 서버가 양쪽에 각각 접근해서, 파일 자체는 S3에 올리고 그 파일의 경로나 메타데이터만 RDS에 한 줄 적어두는 식이다. 그래서 체인이 아니라 옆으로 나란히 있는 것으로 볼 수 있다.

그러니까 서버와 RDS가 있었다면 클라이언트 -> 서버 -> S3(파일) + RDS(기록) 이 되었을텐데, 지금은 둘 다 없기 때문에 클라이언트 -> S3 방식으로 채택이 되어 있는 것이다. 좋은 점은 서버와 RDS를 거치지 않기 때문에 병목이 없고, 가격적인 면에서도 이득이 크다.

### 그렇다면 우리는 왜 지금도 서버가 없을까

당장은 서버가 필요하지 않기 때문이다. 그럼 서버가 있어야하는 이유는 뭘까? 이걸 고민해봤는데, 바로 위의 IAM 키 얘기가 답 중 하나였다. 클라이언트를 못 믿는 일이 생기는 순간 서버가 필요해진다. 키를 대신 쥐고 있어야 할 때, 누가 뭘 할 수 있는지 확인해야 할 때, 남의 데이터를 못 건드리게 막아야 할 때이다. 

현재 우리는 S3에 사용자들이 로컬에 저장해두었던 데이터를 업로드하고 있다. 그러니 서버가 필요하지 않는 상황이다.

## EAS prod URL

앱을 배포해본적이 없었기 때문에 EAS Build를 소마 프로젝트 진행하면서 사용하고 있는데, 전에 웹으로만 개발할 때는 EIP를 설정하고 그걸 클라이언트 단에 줘서 연결하는 방식이었는데 이번엔 그런게 전혀없었다. 알고보니 EAS의 json에 이미 prod API URL을 넣어두었고, 빌드가 될 때 그게 내장되는 방식이었다.

처음엔 이게 보안적으로 좋다고 생각했다.(앱을 개발 안해봐서) 그 이유도 외부에서 빌드를 까보지 않는 이상 노출되지 않으니까였다. 근데 사실 이 생각은 틀렸다. 앱 번들은 까보기 어려운 것이 아니기 때문에 그냥 압축 파일이라 받아서 풀면 안에 들어간 문자열이 다 보일 수 있다. 빌드에 값을 넣는 건 숨기는 게 아니라 그냥 같이 배포하는 것이다.

그래서 기준이 이렇게 갈린다.

- API URL 정도는 넣어도 된다. 어차피 앱이 그 주소로 통신하니까 통신만 들여다봐도 나온다.
- 키나 시크릿은 절대 넣으면 안 된다. 위의 IAM 키도 클라이언트가 들고 있는 이상 정확히 같은 문제다.

## Terraform (현재는 Pulumi 사용 중)

AWS EC2나 RDS를 주로 세팅할 때 항상 GUI에서 했는데, Terraform을 사용하면 이런거 없이 CLI 화면에서 모든걸 세팅할 수 있다고 한다. 그럼 얼마나 편리한가? GCP처럼 CLI 화면에서 버킷도 생성하고, 관리할 수 있는게 좋은 것 같다.

좀 더 정확히는 CLI로 명령을 하나하나 치는 게 아니라, 인프라를 코드 파일로 적어두고 plan으로 뭐가 바뀔지 미리 보고 apply로 반영하는 방식이다. 코드니까 git에 올라가고, 그래서 누가 무엇을 바꿨는지 알 수 있고 PR로 리뷰도 가능한 것이었다.

그리고 몰랐던 것 하나. Terraform은 state 파일이라는 걸 들고 있다. 코드와 실제 AWS 상태를 대조하는 장부 같은 건데, 이게 있어야 plan이 뭐가 바뀔지를 계산할 수 있다. 팀으로 쓸 거면 이 state를 공유 저장소에 두고 잠금을 걸어야 한다고 한다. 특히, AWS내에서 다른 계정으로 이주할 때 편리한 것도 결국 코드와 이 state가 있어서다.

현재는 멘토님 추천으로 Pulumi를 사용중인데 이게 더 개발자 친화적이라고 한다. 찾아보니 약간 명령어는 다르지만, 완전한 프로그래밍 언어로 모든걸 다 할 수 있다고 한다. plan, apply나 state 같은 개념은 그대로고 설정을 HCL 대신 TypeScript나 Python으로 쓰는 차이인 것 같다.

처음에 그래서 AWS CLI와 Pulumi가 뭔 차이인데?! 라고 하고 있다가 결국 에어컨으로 따졌을 때 25도라는 적정 온도를 알아서 맞춰줘와 25도를 맞추기위해 버튼을 위 아래로 누르는 그 차이라고 이해하였다.

이 부분도 앞으로 사용해보면서 차근차근 익혀보려고 한다.
