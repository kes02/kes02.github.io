### 알고리즘 문제 메일로 배달해 드립니다

알고리즘 스터디를 하다 보면 가장 큰 페인 포인트가 하나 있습니다. **"오늘 뭐 풀지?"** 그리고 "누가 이 문제 풀었었나?"를 매번 확인하고 소통하는 과정이 생각보다 에너지를 많이 잡아먹는다는 점이었습니다.

지난번에는 이 문제를 해결하기 위해 출제 보조 웹 서비스를 만들었지만, 문득 이런 생각이 들었습니다.

> "사용자가 매번 우리 사이트에 접속해서 문제를 확인해야 할까? 그냥 알아서 메일로 보내주면 더 편하지 않을까?"

그래서 기능을 추가했습니다. **백엔드 서버 없이 구현하는 '알고리즘 문제 구독 서비스'** 개발 수기입니다.

-----

### 기술 스택

**별도의 백엔드 인프라 구축 없이 GitHub Pages 환경에서 배포와 자동화를 끝내는 것**이었습니다.

  - **Frontend:** HTML, CSS, JS
  - **Database:** Supabase (PostgreSQL & Auth)
  - **Automation:** GitHub Actions (메일 발송 스케줄러)
  - **Mail:** Nodemailer & Gmail SMTP

### 개발 중 마주친 기술적 챌린지

#### 1. GitHub Actions의 'Cron'은 정각에 돌지 않는다?

가장 고민되었던 점은 GitHub Actions의 스케줄러 지연 문제였습니다. 9시 정각에 설정해도 서버 상황에 따라 15\~20분씩 늦게 돌아가는 현상이 발생할 수 있습니다.

**해결책: "시간 차이"가 아닌 "발송 상태"로 관리하기**
"지금이 9시인가?"를 체크하는 대신, DB에 `last_sent_date` 컬럼을 추가했습니다.

  - **로직:** `설정 시간이 지났는가?` AND `오늘 아직 메일을 안 보냈는가?`
    이 방식을 통해 서버가 10분 늦게 깨어나더라도 누락 없이 당일 메일을 안전하게 발송할 수 있도록 방어 로직을 구축했습니다.

#### 2. Supabase Free Tier의 메일 발송 제한

무료 플랜에서는 인증 메일 발송 제한(Rate Limit)이 타이트하기 때문에 테스트 과정에서 `429 에러`가 발생하게 되었습니다.
토이 프로젝트 단계에서는 `Confirm Email` 설정을 유연하게 조절하고, 추후 확장성을 위해 외부 SMTP 서비스(Resend 등) 연결을 고려하는 등 서비스 운영 관점의 고민을 할 수 있었습니다.

#### 3. 수신이 가능한 메일만을 DB에 등록

정식은 아니지만 웹사이트로 오픈할 경우 여러 사람들이 사용해보기 때문에 분명 자신의 이메일이 아니거나, 존재하지 않는 이메일 등록에 대한 문제가 발생할 수 있습니다.
**해결책: 이메일 인증을 통해 DB 등록**
  - **로직:** `처음 문제 구독을 했는가` OR `이미 문제 구독을 한 기록이 있는가 `
    구독을 신청할 시에 Supabase에서 제공하는 Email 기능을 사용하여 구독을 신청할 시 인증 완료 버튼을 눌러야 구독 신청이 완료되도록 하였습니다.
마찬가지로, 구독 내용 변경 시에도 동일하게 이메일 확인이 완료되어야 DB에 반영될 수 있도록 하였습니다.

### 해결해야할 문제점
- 구독 설정 변경을 위해 신청한 기기 또는 웹이 다를 경우 이메일 인증을 완료하더라도 DB에 업데이트 되지 않는 문제가 있기 때문에 하나의 디바이스에서 모든걸 해결해야합니다.
	- 예를 들면 chrome 탭에서 구독 설정 변경을 신청했는데 모바일에서 인증한다면 DB에 업데이트가 되고 있는 않는 상황

### 마치며

단순히 "웹사이트를 만든다"에서 그치지 않고, "어떻게 하면 사용자가 더 편하게 이 기능을 누릴 수 있을까?"를 고민하며 구독 시스템까지 확장해 보았습니다.

백엔드 서버 한 대 없이도 Supabase와 GitHub Actions의 조합만으로 꽤 훌륭한 자동화 서비스를 만들 수 있다는 것을 다시 한번 체감했습니다. 

개발한 페이지는 오픈되어 있으나 Supabase Free로 인해 Email Send limit가 있는 상태로 원활하게 테스트가 안 될 가능성이 높습니다.
