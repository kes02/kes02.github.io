백오피스에서 라벨링을 하기 위해 데이터를 확인하던 중에 특이하게 안드로이드 사용자 세그먼트의 '학습 단어' 칸만 전부 **삭제된 단어**로 표시되어 있었다. 
처음 이 현상을 확인했을때는 당연히 사용자들이 등록한 뒤에 삭제했다 라고 생각했지만 계속해서 지켜보니 아이폰 사용자들 녹음은 있는데, 안드로이드 사용자만이 '삭제된 단어'로 표시되고 있다는 것을 확인했다. 그래서 설마...? 포맷 validate에서 걸려서 빈 채로 올라오나?라고 의심하게 되었다.

## 발생 이유

백오피스에서는 세그먼트 메타데이터를 DB에서 가져오게 되고, 단어 행을 못 찾으면 `word_deleted = true`로 표시한다.

```js
// buddybird-audio-labeling/scripts/app/static/segments.js
['학습 단어', info.word || (info.word_deleted ? '삭제된 단어' : '-')],
```

```python
# scripts/integrations/pull_metadata_from_db.py
# 유저가 단어를 삭제하면 행이 사라져 복원 불가 → word=null, word_deleted=true
```

그래서 이 코드로는 '사용자가 지웠다'와 '업로드 실패'를 구분하지 못한다. 그래서 처음에 단어 삭제가 많다는 것을 봤을 때 사용자 행동으로 읽게 되었다. 특히, 아이폰 사용자들과 안드로이드 사용자들의 비율이 비슷하고 초기에는 업로드 되는 데이터가 많지 않았다보니 확인이 늦어지게 되었다.

## 업로드 경로를 하나씩 확인

단어 오디오는 아래 순서로 서버에 올라간다.

**1단계: 클라이언트가 MIME을 붙인다.** 파일 확장자에서 타입을 유도한다.

```ts
// buddybird-mobile/features/word-library/word-upload-request.ts
function resolveMimeType(uri: string): string {
  const extension = uri.split('?')[0]?.split('.').pop()?.toLowerCase();
  if (extension === 'm4a') return 'audio/x-m4a';
  if (extension === 'mp4') return 'audio/mp4';
  ...
}
```

녹음 파일은 iOS든 안드로이드든 `.m4a`다. 그래서 클라이언트가 보내는 값은 양쪽 다 `audio/x-m4a`. 

**2단계: 서버가 다시 확인한다.** 파일 내용을 직접 읽어 다시 판별한다. 

```python
# app/word/application/use_cases/command/create_word.py
audio_file=AssignFileCommand(
    name=data.audio_file.name,
    type=self._file_analyzer.get_mime_type(file=data.audio_file.file),  # libmagic
    file=data.audio_file.file,
),
```

**3단계: 판별된 타입을 allowed 리스트에 대조한다.**

```python
# app/word/domain/entities/word.py
file.validate(
    allowed_types=["audio/mpeg", "audio/wav", "audio/x-wav", "audio/aac", "audio/mp4", "audio/x-m4a"],
    max_size="5MB",
)
```


## 원인

안드로이드 녹음 파일을 libmagic으로 호출하면 `video/mp4`가 나온다.

expo-audio의 `RecordingPresets.HIGH_QUALITY`는 안드로이드에서 **mpeg4 컨테이너 + AAC 인코더**로 녹음한다. 앱 코드가 정한 게 아니라 프리셋 기본값이고, 실제 컨테이너를 쓰는 건 OS의 MediaMuxer다. 확장자만 `.m4a`일 뿐 파일 헤더의 ftyp 브랜드는 iOS가 쓰는 `M4A `와 다르다. 내용 기반 판별기는 헤더를 보므로 안드로이드 파일은 `video/mp4`가 된다.

`video/mp4`는 allowed 리스트에 없었다. 그 결과 `NotAllowedFileTypeException` → 400.

iOS 파일은 `audio/x-m4a` 또는 `audio/mp4`로 판별돼 목록을 통과했고 같은 앱, 같은 코드, 같은 `client_word_id`와 uid를 보내는데 OS 하나 차이로 업로드가 안 되고 있었다.

## 왜 S3에서 문제 확인이 불가했는가?


```python
word = Word.create(command=command)   # ← 여기서 검증 실패
await self._word_repo.save(word=word)

audio_file_path = f"{word.audio_file.file_path}/{word.audio_file.file_name}"
on_rollback(partial(self._object_storage_client.delete, path=audio_file_path))
await self._object_storage_client.upload(path=audio_file_path, file=data.audio_file.file)
```

검증 로직은 `Word.create()` 안에 있고, DB 저장과 S3 업로드는 그 뒤다. 400을 response 받으면 다음이 실행되지 않게 되기 때문 S3에도 안 올라가게 되고 결국 빈 상태로 업로드 되는 것이다.

여기에 문제가 하나 더 있었는데 클라이언트는 4xx를 '서버가 거부한 요청'으로 보고 재시도하지 않게된다. 그 결과로 **거부된 녹음은 영구 손실**이었다. 

## 확인이 늦은 이유

크래시가 아니었고 앱에 문제도 없었고, 예외 리포트도 안 올라가고, 서버는 200이 아니라 400을 정상적으로 응답했다. 서버 입장에선 '허용되지 않는 파일을 거절함'이라는 의도된 동작이기 때문이다.

그래서 알아챈 경로가 앱도 모니터링 도구도 아닌 **라벨링 도구**였다는 게 핵심이다. 플랫폼별 업로드 성공률 지표가 없으면 사용자 절반의 데이터가 통째로 비어도 대시보드에는 아무 일도 안 일어난다. 수집 파이프라인의 실패는 보통 이렇게 생긴다는 것을 처음 알게 되었다.

## 해결 및 느낀점
- 누락된 포맷을 코드 상에 추가했고, 현재는 안드로이드와 iOS 모두 차이 없이 업로드 되는 것을 확인했다. 추후 오디오를 다루는 업무를 맡게 된다면 이 부분을 유의할 수 있을 것이다.
- 수집 파이프라인에서 공백은 사람이 아니라면 찾기 어려웠을 것이다. 에러나 모니터링 도구에서는 전혀 파악되지 않았기 때문에 사용자 측에서 업로드되어 관리해야하는 데이터에 한해서는 수집한 데이터의 성공률 지표를 볼 수 있도록 해야겠다.
