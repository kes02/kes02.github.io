도커를 배우게 된다면 이어서 당연하게도 쿠버네티스에 대해 알아야한다.
쿠버네티스는 다른 이름으로 k8s으로 불리는데, 이것은 kubernetes k부터 s사이에 8 글자가 있다는 의미에서 불린다고 한다.
그리고 컨테이너 오케스트레이션 도구에 걸맞는 조타수 모양이다.

## 쿠버네티스란?
컨테이너의 상태를 바람직한 상태로 유지해주는 도구라고 할 수 있다. 즉, 컨테이너의 상태를 관리해주는 도구이다.
여기서 바람직한 상태?라는 것이 애매할 수 있다.
그리고 이 바람직한 상태를 쿠버네티스는 데이터 저장소에 저장해두고 계속해서 이 상태를 유지한다.
이것을 마스터 노드와 워커노드가 관리하게 되는데 이름에서 나와있듯이 **마스터 노드**가 **워커노드의 상태를 관리**하는 것이다.

### 바람직한 상태?
쿠버네티스에 우리가 미리 설정해둔 파일이 저장된 **etcd**이라는 **DB**에서 요구하는 상태를 바람직한 상태라고 할 수 있다. 
### etcd
etcd는 단순한 파일 저장소가 아니라 '클러스터의 뇌' 역할을 하는 키-값(Key-Value) 저장소이다.
사용자가 **kubectl apply**로 **매니페스트**를 던지면, 마스터 노드는 이 내용을 etcd에 기록하고, 실제 상태가 이 기록과 다르면 워커 노드에 명령을 내려 상태를 일치시킨다.

그럼 미리 설정해둔 파일이라는 것은 어떻게 설정할 수 있는가?

## 매니페스트 파일 (ManifestFile)
도커에서 Dockerfile을 통해 컨테이너의 환경을 미리 세팅할 수 있듯이 쿠버네티스에서는 이 manifestfile을 통해 설정할 수 있다. 또한, yaml 파일 형태를 주로 사용한다.
매니페스트 파일은 리소스 단위로 작성한다. 여기서 리소스란 파드나 서비스, 디플로이먼트, 레플리카셋 등을 가리킨다.

### 파드? 서비스? 디플로이먼트? 레플리카셋?
- 파드: 컨테이너의 정보가 포함되어 있다. name, image, ports
- 레플리카셋: 이름에서 알 수 있듯이, 여러개의 컨테이너의 형태를 뜻한다.
- **서비스**: 특정 컨테이너로 연결되는 역할
- **디플로이먼트**: 파드의 생성과 삭제를 관리해주는 역할

### 그럼 어떻게 작성하면 좋을까?
보통은 서비스와 디플로이먼트 파일만 작성하게 된다. 그 이유는 디플로이먼트가 레플리카셋을 '관리'할 수 있기 때문에, 서**비스 매니페스트 파일과 디플로이먼트 매니페스트 파일**만을 사용한다.

우리가 디플로이먼트를 만들면, 디플로이먼트가 레플리카셋을 만들고, 그 레플리카셋이 파드를 개수만큼 유지합니다. 즉, 우리는 가장 상위 관리자인 디플로이먼트만 만들면 되는 것이다.

이 매니페스트 파일에 필수적인 부분은 apiVersion, kind, metadata, spec 이다.

### 디플로이먼트 매니페스트 파일
- 역할: 파드의 관리 (파드 내부의 컨테이너도 관리)
예시로 작성해본다면 아래와 같은 형태일 것이다.
```yaml
apiVersion: apps/v1
kind: Deployment 	<- 리소스 유형
metadata: 
  name: apa000dep 	<- (중항목) 디플로이먼트 이름
spec:
  selector: 		<- (중항목) 셀렉터 설정
    matchLabels: 	<- (소항목) 셀렉터가 선택할 관리 대상 레이블
      app: apa000kube
  replicas: 3		<- (중항목) 레플리카 설정
  template: 		<- (중항목) 템플릿(파드의 정보_
    metadata: 		<- (소항목) 파드의 메타데이터를 기재
      labels:
        app: apa000kube
    spec: 			<- (소항목) 파드의 스펙을 기재
      containers:
      - name: apa000ex91
        image: httpd
        ports:
        - containerPort: 80
```
- 셀렉터 설정: 디플로이먼트가 특정한 레이블이 부여된 파드를 관리할 수 있도록 하는 설정
- 레플리카 설정: 파드 수를 '몇 개로 유지'할 것인지 설정
- 템플릿 작성: 파드에 대한 정보를 기재
- spec의 아래 부분: 파드 매니페스트 파일에 적는 내용

### 서비스의 매니페스트 파일
- 역할: 파드로 들어오는 요청을 관리 (로드밸런싱과 관련), 접근 관리(통신)
``` yaml
apiVersion: v1
kind: Service
metadata:
  name:	apa000ser		<- (중항목) 서비스의 이름
spec:
  type:	NodePort		<- (중항목) 서비스의 유형
  ports:				<- (중항목) 포트 설정
  - port: 8099 			<- (중항목) 서비스의 포트
  	targetPort:	80		<- (소항목) 컨테이너의 포트
    protocol: TCP		<- (소항목) 통신에 사용되는 프로토콜
    nodePort: 30080		<- (소항목) 워커 노드의 포트
  selector: 			<- (중항목) 셀렉터 설정
  	app: apa000kube
```

유형은 서비스의 종류를 말하며 어떤 유형의 IP주소로 접근할지를 결정한다.
4가지가 있고, ClusterIP, NodePort(워커 노드의 포트), LoadBalancer, ExternalName이 있다.
보통 실무에서는 **LoadBalancer**를 주로 사용한다.
포트를 비유한다면 nodePort는 우리가 사는 아파트 입구의 비밀번호, port(서비스의 포트)는 아파트 동의 비밀번호, targetPort는 우리집 비밀번호 라고 이해할 수 있을 것 같다.

## 쿠버네티스의 명령어
**kubectl 커맨드 옵션** 으로 작성하면 된다.
필수적으로 알아야하는 커맨드는
- create: 리소스 생성
- delete: 리소스 삭제
- get: 리소스 상태 출력 (ex. kubectl get pods)
- set: 리소스 값 설정
- apply: 리소스 변경 사항 반영 (ex. kubectl apply -f [디플로이먼트 매니페스트 파일 위치])
- scale: 레플리카 수 변경
- logs: 컨테이너의 로그 화면 출력

### 그렇다면 우리는 쿠버네티스를 어떻게 사용할 수 있을까?
보통의 기업에서는 정통적인 쿠버네티스를 사용한다고 한다. 그러나 우리는 GCP(GKE)나 AWS(EKS) 같은 클라우드 환경에서 제공하는 로드밸런서를 자동으로 생성해 주는 유형으로 사용할 수 있다.
또한 앞에서 설명한 도커 데스크탑에 내장 되어있는 쿠버네티스를 활용할 수도 있다.

실무에서는 외부 노출을 위해 LoadBalancer를 쓰지만, 클러스터 내부 끼리의 통신(예: API 서버와 DB 사이)에는 ClusterIP가 기본값으로 사용된다는 점도 기억하면 좋을 것 같다.

### 최종 정리
- 클러스터: 단일 마스터노드와 여러개 또는 한개의 워커노드로 구성
- 워커 노드(Worker Node): 실제 서버 (하드웨어/VM)
- 파드(Pod): 워커 노드 안에서 돌아가는 가장 작은 배포 단위
- 컨테이너(Container): 파드 안에 담긴 실제 프로그램 (프로세스)
