앵무새 소리를 판정하는 AI 모델을 서비스 내에 기능으로 넣기 위해 기존에 존재하는 api 서버 외에 audio-ai 서빙과 ai 판단을 위한 서버를 두게 되었다. 앱에서는 사용자가 학습시키면서 발생한 소리를 서버가 받고, 서버에서 요청을 보내면 앵무새가 낸 소리인지 판정하고, 학습 중인 단어를 따라 한 건지 판정해주는 AI를 붙일 예정이었다. 

고민은 API 서버와 AI 서버를 어떤 방식으로 연결할지였다.

## 처음엔 gRPC로 채택

며칠 전 AI 서버를 gRPC 서버로 전환하는 작업이 끝나 있었다. AI 서버는 RestAPI를 사용하지 않고 판단한 결과값만 API에 전달하는 방식으로 바뀌어서 FastAPI를 걷어내고 빠르게 동작할 수 있는 gRPC를 채택해 proto를 정의해두었다.

그러고 나서 고민을 해보니 큐가 있다면 gRPC를 사용하지 않아도 된다는 것을 알게 되었다. gRPC에서 큐로 바뀐 이유는 결과값만 보내기 때문에 굳이 gRPC를 사용할 필요가 없었던 것이었다.

## 결국 큐를 채택한 이유

gRPC는 전화에 가깝다. 걸면 상대가 받아서 그 자리에서 답한다. 답을 받을 때까지 기다려야 하고, 상대가 꺼져 있으면 실패하는 형태이다.

반대로 큐는 우체통이다. 편지를 넣으면 내 할 일은 끝난다. 상대가 자리에 없어도 편지는 남아 있고, 나중에 꺼내 읽는다. 대신 답이 언제 올지는 모른다.

그래서 기준은 '어느 쪽이 더 적절할까'가 아니라 '이 작업이 답을 기다려야 하며 데이터 손실이 발생해도 괜찮은가'였다. 답은 확실하게 No였다. API가 문제가 발생해 응답을 받지 못하게 되고 그대로 사용자 데이터가 손실이 발생하게 된다면 문제였다. 그래서 gRPC를 걷어내고 큐로 채택하게 되었다.

## AI 서버에서 사용하는 2가지 기능

**onset 분석**은 앵무새가 짧은 울음을 촘촘히 반복하는 구간을 찾아낸다. 반복 횟수와 구간 길이를 보고 응급 후보인지 가린다. 현재는 응급 후보에 대한 데이터 확보가 어려워, 신경질적 짹짹과 같이 흥분한 구간을 가려내도록 사용하고 있다. -> 이 기능은 손실이 나면 안되는 부분

**소리 판정과 모사 판정**은 세션이 끝나고 녹음된 걸 모아서 판정하면 된다. 결과가 몇 분 늦어도 사용자 경험에 차이가 없다. 대신 모델이 무거워서 한 건에 수백 초가 걸릴 수 있다. -> 손실이 난다면 다시 데이터를 읽고 판정하면 되는 부분

=> 최종적으로 실시간 결과값 서빙을 위해 큐로 동작

## 결론 및 배운점

```
API 서버 ──── SQS 큐 ────▶ AI 서버     onset 판정, 소리·모사 판정
```

처음엔 배치를 넣어야하나?라는 고민도 했지만 API는 기능, AI 서버는 API 서버가 보낸 응답에 대한 결과값만 보내는 역할이라 이런 부차적인 고민을 하지 않고 신뢰성있는 결과값을 주고 받을 수 있는 것만 고려하여 큐로 채택했다.

기존에 서비스를 하면서 AI 모델을 서빙하는 서비스를 해보지 않았기 때문에 어디에 모델을 서빙하는 기능을 두고 어떻게 동작시킬지에 대한 고민을 해본적이 없었는데 이번 프로젝트를 진행하면서 여러 고민들을 할 수 있었다.
1. AI 모델을 백엔드에 둘지
2. AI 모델은 어떤 역할만 할지
3. Hugging Face에 올라간 AI 모델을 어떻게 다운로드 받고 사용자에게 빠르게 서빙할 수 있을지
