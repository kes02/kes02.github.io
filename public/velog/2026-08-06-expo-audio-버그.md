# 시뮬레이터에선 되는데 TestFlight에선 안 되는 버그

디버깅하기 제일 까다로운 버그는 세 가지가 겹칠 때라고 생각한다. 간헐적이고, 실패해도 티가 안 나고, 개발 환경에선 재현이 안 되는 것. 이번 건이 딱 그랬다.

우리 앱에는 보호자가 자기 목소리로 단어를 녹음하는 기능이 있다. 앱스토어 리뷰에 녹음이 안 된다는 글이 올라와서 바로 확인해봤는데, 설치한 앱에서도 시뮬레이터에서도 멀쩡했다. 코드를 계속 들여다보다가 실기기에서 가끔씩 실패한다는 걸 알게 됐다. Firebase에 잡히는 오류는 당연히 없었다. 녹음 화면은 정상이고 타이머도 잘 흐르는데, 저장된 파일을 재생해보면 소리가 없었다.

## 버그 재현

| 빌드 | 결과 |
|---|---|
| 시뮬레이터 (Debug) | 정상 |
| 실기기 로컬 설치 (Debug) | 정상 |
| 실기기 TestFlight (Release) | 간헐적 실패 |

같은 코드, 같은 기기인데 설치 경로에 따라 결과가 갈렸다. 실기기 Debug가 정상이니 기기 문제는 아니고, 시뮬레이터와 로컬도 정상이니 코드 로직 자체가 틀린 것도 아니다. 남는 변수는 Debug와 Release의 차이뿐이었다. 여기에 ‘간헐적‘이라는 단서를 합치면 타이밍 문제, 그러니까 레이스를 의심하려고했다. 

먼저 배제한 게 하나 있다. 이 앱에는 학습 세션이 마이크를 점유해서 녹음이 실패하는 별개 버그(BB-247)가 있었다. 그런데 이번 건은 세션을 한 번도 시작하지 않은 상태에서도 발생했고, BB-247 쪽에서 확인한 버그는 ‘녹음을 시작하지 못했어요‘라는 문구라도 띄웠다. 이번 건은 그 문구조차 없었기 때문에 다른 버그였다.

## Why
### 그렇다면 expo-audio가 예약해두는 세션 해제인가?

`AudioModule.swift`를 따라가면 이런 동작이 나온다. `player.pause()`는 `keepAudioSessionActive` 옵션이 false면(기본값이 false다) `deactivateSession()`을 호출한다. `deactivateSession()`은 100ms 뒤에 실행될 블록을 예약한다. 그리고 그 블록은 재생 중인 player가 있는지만 확인하고, 없으면 `setActive(false)`로 iOS 오디오 세션을 내려버린다. recorder는 확인하지 않는다.

여기에 우리 앱의 녹음 시작 흐름을 겹쳐보면 그림이 맞는다. 녹음 버튼을 누르면

1. 재생 중일 수 있는 미리듣기 player를 정지한다. `player.pause()`가 불리면서 100ms 뒤 세션 해제가 예약된다.
2. 마이크 권한을 확인한다.
3. 오디오 모드를 녹음용으로 전환한다.
4. `prepareToRecordAsync()`와 `record()`로 녹음을 시작한다.

2~4번이 100ms 안에 끝나면, 예약된 해제 블록이 깨어났을 때 재생 중인 player는 없다. 즉, 마이크는 형식상 돌아가지만 이미 세션이 죽었으니 들어오는 소리가 없고, 그대로 무음 파일이 저장된다.

반대로 2~4번이 100ms를 넘기면 해제가 `record()` 전에 끝나고, 이후 오디오 모드 전환이 세션이 생기기 때문에 아무 일도 일어나지 않는다.

```
─── 100ms 안에 record()가 시작되는 경우 (실패) ───
pause() ──▶ [100ms 타이머] ─────────▶ 세션 해제
                 └─ 권한 → 모드 전환 → record() 시작됨
                                        (녹음 중인데 세션이 내려감, 무음)

─── 100ms를 넘기는 경우 (정상) ───
pause() ──▶ [100ms 타이머] ▶ 세션 해제 (무해)
                              └─ 모드 전환이 세션 재활성화 → record() 정상
```

### 왜 TestFlight나 실기기에서 발생했을까? 

이제 빌드 매트릭스가 설명된다. Release 빌드는 Hermes 바이트코드로 실행되고, Debug 빌드는 Metro dev server를 거친다. JS와 네이티브 사이 왕복이 Release 쪽이 훨씬 빠르다. 즉, 시뮬레이터가 실행되는 노트북의 성능이 이 버그를 일으키지 않은 것 이었다.

시뮬레이터와 로컬 Debug가 정상으로 보였던 건 코드가 맞아서가 아니라 느려서였다. 버그는 처음부터 모든 빌드에 있었고, 레이스의 승패만 빌드 구성에 따라 갈렸을 뿐이다. Release 안에서도 그때그때 체인 소요 시간이 100ms 언저리를 오가니까, 같은 조작에서 됐다 안 됐다 하는 간헐성도 여기서 설명된다.

expo 저장소를 찾아보니 같은 모양의 이슈가 있었다.([expo/expo#41656](https://github.com/expo/expo/issues/41656)). 다른 컴포넌트가 오디오 세션에 간섭해서 실기기에서만 빈 녹음 파일이 생기고 시뮬레이터는 정상이라는 내용이다.

### 왜 오류를 확인할 수 없었을까

이 버그는 앞에서 말했든 firebase의 crashlytics에서 확인이 불가능했다.

네이티브의 세션 해제 실패나 간섭은 Swift 쪽 `print`로만 남고 JS로는 올라오지 않는다. JS의 녹음 상태는 `'recording'`으로 유지되고, 경과 타이머도 recorder가 아니라 자체 인터벌로 도니까 계속 흐른다. 화면만 보면 완벽하게 정상이다. 저장 직전 파일 검사도 없다. `if (!audioRecorder.uri)` 가드는 있지만 기본 초기화된 recorder도 uri가 비어 있지 않아서 걸리지 않고, 크기나 길이 검사는 아예 없다. 심지어 "너무 짧은 녹음" 안내 문구(`tooShortMessage`)는 선언만 되고 쓰이지 않은 채 코드에 남아 있었다

## 해결

원인이 pause()가 예약하는 암묵적 세션 해제니까, 그 예약이 아예 생기지 않게 하면 된다. 찾아본 결과 expo-audio가 옵션을 제공하고 있었다.

```ts
// use-audio-preview.ts
// keepAudioSessionActive: expo-audio는 pause()·재생 완료 시 0.1초 뒤 iOS 오디오 세션을
// 비활성화하는데, 이때 녹음 중인 recorder를 확인하지 않아 녹음 시작 직전 stopPreview()의
// pause()가 실기기에서 진행 중인 녹음을 무음으로 만든다. 세션 활성화는 audio-mode.ts가 관리한다.
const player = useAudioPlayer(null, {
  updateInterval: PLAYER_UPDATE_INTERVAL_MS,
  keepAudioSessionActive: true,
});
```

앱에서 player를 만드는 두 훅(미리듣기, 캡처 재생) 모두에 `keepAudioSessionActive: true`를 켰다. 이러면 pause()가 세션 해제를 예약하지 않으니 경합 자체가 사라진다. 세션을 켜고 끄는 책임은 앱의 audio-mode 모듈 한 곳으로 모았고, 코드 상에서 다루는 쪽으로 해결하였다.

## 고민

레이스는 사라졌지만, 조사하면서 드러난 구조적 문제가 하나 더 있다. 같은 증상이 다른 원인으로 또 생기면 여전히 조용히 지나간다는 것.

- 저장 후 파일 크기를 검사해서 빈 녹음이면 사용자에게 알려주는 안전망이 필요하다. 크기를 재는 함수는 이미 코드에 있는데 다른 경로에서만 쓰인다. 놀고 있는 `tooShortMessage`를 여기 연결하면 되는데, 사용자에게 이를 꼭 알려주어야할까? 사용자에게는 ‘다시 녹음하세요‘만 보여줘도 되지 않을까?

## 느낀 점

시뮬레이터에서 QA를 하는건 검증이라고 할 수 없는 것 같다. 시뮬레이터 Debug, 실기기 Debug, 실기기 Release는 서로 다른 환경이고, 특히 오디오나 타이밍이 얽힌 기능은 Release 구성으로 실기기에서 꼼꼼히 확인해야 한다. 이를 위해서 QA 항목을 정리하고, E2E 테스트를 도입해야할 것 같다는 생각이 들었다.

앱을 개발함에 있어서 버그는 끊임없이 발생하기 때문에, 체계적인 QA 시스템과 함께 잠재적인 버그가 발생할 수 있는 구간을 찾아내는게 AI를 활용한 개발에서 특히 중요하게 작용할 것 같다.
